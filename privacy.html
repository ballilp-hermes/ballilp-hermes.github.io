Privacy Policy — Hermes Personal Assistant

Last updated: 13 November 2026 · Effective immediately · Version 2.0

This policy explains, in full, what data Hermes Personal Assistant (“the application”) accesses, why it accesses it, where that data is stored, how long it is kept, who it is shared with, and how the person whose account is connected can withdraw access or have data deleted.

There is exactly one such person: the owner of the Google Account that authorises the application. The application has no other users, and it cannot reach any other person's Google Account.

1. Who operates the application, and who is responsible

The application is operated by its owner — a private individual based in Hong Kong — strictly for that individual's own personal and administrative use. It is not a commercial service, is not offered to the public, and has no customers.

The operator is the data controller for the purposes of this policy, and is also the only data subject. Contact for any privacy question, access request or deletion request: sales@link-point.org. This address is monitored by the operator.

2. What the application is, and what it is not

It is a desktop automation tool that runs locally on the operator's own computer and performs administrative tasks on request — for example adding a calendar event, sorting an inbox, or producing a document from the operator's own files.

It is not a public product. There is no sign-up, no user accounts, no dashboard, no subscription, no advertising and no analytics. It is not published in an app store, is not distributed to third parties, and is not operated as a service for anyone else.

3. What Google user data is accessed, and exactly why

Data is accessed only after the operator reviews and approves Google's OAuth 2.0 consent screen, and only within the scopes granted there. Each scope and its purpose:

ScopeWhat it gives access toWhy the application needs it
calendarThe operator's own Google Calendar: events, titles, times, locations, descriptions, reminders.To list upcoming events and to create, or update, events the operator asks for.
gmail.readonlyRead access to the operator's own Gmail messages, threads, labels and attachments.To search and summarise mail when the operator asks, for example to triage an inbox.
gmail.modifyThe ability to apply or remove labels, mark messages read or unread, and file messages.To organise mail on the operator's instruction — labelling, archiving and drafting.
gmail.sendThe ability to send mail from the operator's own address.To send a message, only after the operator has reviewed and approved that specific message.
driveFiles in the operator's own Google Drive.To locate, read, upload and organise the operator's own files when asked.
spreadsheetsThe operator's own Google Sheets, cell ranges and values.To read figures and write rows when the operator asks for a report or tracker update.
documentsThe operator's own Google Docs.To create and edit documents the operator requests.
contacts.readonlyRead-only access to the operator's Google Contacts: names and email addresses.To resolve a name to an email address. Contacts are never created, edited or deleted.

Categories of data involved: calendar event details; email message content, metadata (sender, recipients, subject, date) and attachments; file names and file content in Drive, Sheets and Docs; contact names and addresses. Some of this may include personal data about third parties who correspond with the operator — for example the sender of an email. Such data is processed only as part of the task the operator requested, and is never used for any other purpose.

Data the application does not collect: no passwords, no Google Account credentials, no payment or card data, no location history, no browsing history, no device identifiers, no advertising identifiers, and no data from any Google Account other than the authorising operator's.

4. How the data is used

  • Only to carry out the specific task the operator has requested at that moment, and only for as long as it takes to do it.
  • To display the result of that task back to the operator, on the operator's own machine.
  • No advertising, no profiling, no behavioural analysis, no analytics or telemetry, and no marketing of any kind.
  • No determination of creditworthiness, eligibility, insurance risk, employment or any other consequential decision about any person.
  • No use of Google user data to develop, train, improve or fine-tune generalised or third-party artificial-intelligence models.
  • No sale, rental, licensing or other commercial exploitation of data.

5. Sharing and disclosure

The application does not sell or share Google user data with third parties. Data leaves the operator's computer in only these circumstances:

  • To Google — requests go directly from the operator's machine to Google's own APIs in order to perform the requested task. This is inherent in using the account.
  • To an AI model provider — where a requested task requires language-model processing, the specific content needed for that task is sent to the model provider the operator has configured. Only the minimum content needed is sent, and it is not used by the operator to build any profile.
  • Legal requirement — if disclosure is required by law or by a valid legal process, to the extent strictly required.
  • Security — where necessary to investigate abuse, fraud or a security incident affecting the operator's own account.

No data is transferred to advertisers, data brokers, analytics providers or any other third party for any commercial purpose.

6. Where the data is stored, and for how long

  • OAuth tokens (access and refresh) are stored in a single file on the operator's own computer, readable only by the operator's own operating-system user account. They are retained until the operator revokes access, or until they are replaced during re-authorisation. Revoked and superseded tokens are retained only as an inert backup copy on the same machine and grant no access.
  • Working files and outputs — documents, exports, temporary files and logs produced while doing a task — are stored on that same computer within the operator's own workspace. They are kept while they remain useful for the operator's records and can be deleted at any time.
  • No server-side storage. There is no application back end, database or cloud store holding Google user data. Nothing is retained off the operator's machine except at Google itself, under the operator's own Google Account.
  • Conversation records held by the assistant software may contain excerpts of processed content; they are stored locally, are readable only by the operator, and are deleted when the operator deletes them.

7. Security

  • Authentication uses Google OAuth 2.0 with PKCE; the application never sees or stores the operator's Google password.
  • Tokens are stored with owner-only file permissions on a single computer, and the Google Account is protected by two-step verification.
  • Access can be revoked by the operator at any time and takes effect immediately.
  • No credentials are embedded in this website or in its source. This site is static: it holds no user data and has no database, no cookies, no tracking scripts and no login.
  • No method of storage is perfectly secure; the design choice here is to minimise what exists at all, by keeping the data on one machine under the operator's own control rather than on a server.

8. The operator's rights and controls

Because the operator is the only data subject, these controls are direct and immediate:

  • Revoke access at any time at myaccount.google.com/permissions. The application then loses all ability to read or write the connected Google Account.
  • Delete local data by removing the token file and the workspace files from the computer.
  • Inspect everything the application holds, since all of it sits on the operator's own machine.
  • Withdraw consent for any scope by revoking that scope at the link above, which stops the corresponding capability immediately.
  • Request deletion by writing to the contact address in section 1; the request is carried out by the operator.

9. International transfers

Data is processed on the operator's own computer in Hong Kong. Where a task requires a Google API or an AI model provider, the transmission is made directly to that provider and is governed by that provider's own terms and data-processing commitments. No transfer is made by the operator to any other jurisdiction or party.

10. Children

The application is not directed at, marketed to, or usable by children. It has a single adult user and does not knowingly process any child's data.

11. Google API Services User Data Policy

Limited Use disclosure. Hermes Personal Assistant's use of information received from Google APIs adheres to the Google API Services User Data Policy, including the Limited Use requirements.

Accordingly, the application limits its use of Google user data to providing the features described in section 3; does not transfer Google user data to third parties except as necessary to provide those features, to comply with applicable law, or as part of a merger or acquisition; does not use Google user data for advertising; and does not allow humans to read Google user data except where the operator has given explicit consent for a specific item, where it is necessary for security purposes, to comply with applicable law, or where the data has been aggregated and anonymised.

12. Changes to this policy

Any material change is published on this page with a new “Last updated” date and a version number. Because the application has one user, changes are also communicated directly to that user. Continued use after a change constitutes acceptance of the updated policy.

13. Contact

Privacy questions, access requests, deletion requests, or any concern about this application's handling of data: sales@link-point.org
